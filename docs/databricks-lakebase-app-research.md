# Databricks App + Lakebase Research

Research date: 2026-08-05  
Scope: current official Databricks documentation for building a Databricks App backed by Lakebase on Databricks Free Edition. Sources are Databricks-owned docs unless noted otherwise.

## Short Answer

For a new app on Free Edition, the most Databricks-native path is to create a Databricks App from a Lakebase/database template or custom app, attach Lakebase as an app resource, and let Databricks provide the app service principal, matching Postgres role, permissions, and connection environment variables. Databricks describes this as a fully managed Postgres backend where the app connects without managing credentials or connection strings. Free Edition can support this workflow, but it is quota-limited: up to 3 Databricks Apps, one Lakebase project, serverless-only compute, and apps auto-stop after 24 hours from start/update/redeploy. Sources: [Using Lakebase with Databricks Apps](https://docs.databricks.com/aws/en/oltp/projects/databricks-apps), [Add a Lakebase resource to a Databricks app](https://docs.databricks.com/aws/en/dev-tools/databricks-apps/lakebase), [Databricks Free Edition limitations](https://docs.databricks.com/aws/en/getting-started/free-edition-limitations).

## Lakebase / Postgres Connection Basics In Databricks Apps

- Databricks recommends Databricks Apps for new Lakebase-backed apps because the platform manages identity, automatic credentials, and deployment; external apps are for cases that must run outside Databricks or need a specific external runtime. Source: [Build applications backed by Lakebase](https://docs.databricks.com/aws/en/oltp/projects/build-applications).
- Lakebase is exposed to apps as a managed Postgres backend. In the Lakebase Apps tutorial, Databricks says adding Lakebase as a resource creates an app service principal, grants a matching Postgres role, and injects connection details as environment variables so the app can connect without manually managing credentials or connection strings. Source: [Using Lakebase with Databricks Apps](https://docs.databricks.com/aws/en/oltp/projects/databricks-apps).
- Databricks provides Lakebase Autoscaling app templates for Dash, Flask, and Streamlit. The template path is the lowest-friction path for Free Edition because the Databricks UI configures the Lakebase project, branch, and database as an app resource during app creation. Source: [Using Lakebase with Databricks Apps](https://docs.databricks.com/aws/en/oltp/projects/databricks-apps).
- When Lakebase is added as an app database resource, Databricks creates or reuses a Postgres role whose role name matches the app service principal client ID, then grants `CONNECT` and `CREATE` on the selected database. For Lakebase Autoscaling, the user adding the resource must have `CAN MANAGE` on the Lakebase project. Source: [Add a Lakebase resource to a Databricks app](https://docs.databricks.com/aws/en/dev-tools/databricks-apps/lakebase).
- Databricks sets the first database resource's standard Postgres environment variables: `PGAPPNAME`, `PGDATABASE`, `PGHOST`, `PGPORT`, `PGSSLMODE`, and `PGUSER`; `PGUSER` is the service principal client ID / Postgres role name. If an app uses multiple Postgres databases, use `valueFrom` with the resource key instead of relying only on the first-resource variables. Source: [Add a Lakebase resource to a Databricks app](https://docs.databricks.com/aws/en/dev-tools/databricks-apps/lakebase).
- Lakebase can also be reached using standard Postgres clients and drivers. Databricks' Lakebase connection overview covers OAuth roles, Postgres password roles, connection strings, pooling, framework examples, and authentication/token rotation. Source: [Connect to your database](https://docs.databricks.com/aws/en/oltp/projects/connect).
- For custom/manual Lakebase Autoscaling connections, Databricks documents OAuth token rotation: Databricks Apps authenticate to Lakebase with one-hour OAuth tokens, and long-running apps should generate fresh database credentials with the Databricks SDK and a connection pool. This is useful when you are not using the managed template/resource path or need explicit control of the connection lifecycle. Source: [Connect a custom Databricks app to Lakebase](https://docs.databricks.com/aws/en/oltp/projects/tutorial-databricks-apps-autoscaling).

## `app.yaml` Structure And Deployment Path

- `app.yaml` is optional but is the standard file for overriding how a Databricks App runs. It can also be named `.yml`, and it must live at the root of the project directory. Source: [Configure Databricks app execution with app.yaml](https://docs.databricks.com/aws/en/dev-tools/databricks-apps/app-runtime).
- Supported top-level settings documented for `app.yaml` are:
  - `command`: a sequence used when the app needs a custom run command. Defaults are `python <first-python-file>` for Python apps and `npm run start` for Node.js apps. Databricks does not run this through a shell, so external shell environment variables are not automatically available; use `env` for additional parameters.
  - `env`: a list of variables. Each entry has `name` plus either `value` for a literal value or `valueFrom` to reference an external Databricks-managed source such as a secret or database/resource entry.
  Source: [Configure Databricks app execution with app.yaml](https://docs.databricks.com/aws/en/dev-tools/databricks-apps/app-runtime).
- App templates commonly include `app.yaml`, dependency files such as `requirements.txt`, `pyproject.toml`, or `package.json`, and source code. During deployment, Databricks installs dependencies into the app's isolated runtime environment. Source: [Key concepts in Databricks Apps](https://docs.databricks.com/aws/en/dev-tools/databricks-apps/key-concepts).
- Local/workspace deploy path: from the local app directory, upload files with `databricks sync` to a workspace path such as `/Workspace/Users/<email>/<app-dir>`, then deploy with `databricks apps deploy <app-name> --source-code-path /Workspace/Users/<email>/<app-dir>`. Databricks' deploy docs recommend excluding `.env`, `node_modules/`, caches, and large artifacts from sync. Source: [Deploy a Databricks app](https://docs.databricks.com/aws/en/dev-tools/databricks-apps/deploy).
- Git deploy path: configure a Git repository on the app, then deploy a branch, tag, or commit. If the app lives in a subdirectory, pass `source_code_path` in the Git source JSON so Databricks treats that subdirectory as the app root. Source: [Deploy a Databricks app](https://docs.databricks.com/aws/en/dev-tools/databricks-apps/deploy).
- For Lakebase template apps created through the UI, Databricks says app compute starts automatically and the app deploys in about 2-3 minutes after creation. Source: [Using Lakebase with Databricks Apps](https://docs.databricks.com/aws/en/oltp/projects/databricks-apps).

## Credentials, Secrets, And Environment Variables

- Prefer Databricks Apps' app service principal and app resources over personal tokens or hardcoded credentials. Databricks' resource guidance says each app has a dedicated service principal, to use that service principal for authentication, and to never hardcode personal access tokens in code. Source: [Add resources to a Databricks app](https://docs.databricks.com/aws/en/dev-tools/databricks-apps/resources).
- Prefer app resources plus `valueFrom` for environment-specific values. Databricks says resource references connect `app.yaml` environment variables to app resources such as SQL warehouses, secrets, or Lakebase databases. Source: [Define environment variables in a Databricks app](https://docs.databricks.com/aws/en/dev-tools/databricks-apps/environment-variables).
- Do not put secret values directly in source code, `.env`, or the `value` field of `app.yaml`. Databricks says to use `valueFrom` to reference secrets or managed resources so values are retrieved at runtime and not exposed in plaintext configuration. Source: [Define environment variables in a Databricks app](https://docs.databricks.com/aws/en/dev-tools/databricks-apps/environment-variables).
- Databricks supports app secret resources. Secret resources let an app read selected Databricks secrets as environment variables, but secret permissions apply at the secret scope level, so Databricks recommends separate secret scopes per app and least-privilege access. Source: [Add a secret resource to a Databricks app](https://docs.databricks.com/aws/en/dev-tools/databricks-apps/secrets).
- For Lakebase Autoscaling specifically, `valueFrom` resolves to the Lakebase endpoint path, while the first database resource also receives the standard `PG*` variables listed above. Source: [Define environment variables in a Databricks app](https://docs.databricks.com/aws/en/dev-tools/databricks-apps/environment-variables), [Add a Lakebase resource to a Databricks app](https://docs.databricks.com/aws/en/dev-tools/databricks-apps/lakebase).
- If using explicit OAuth token rotation instead of the fully managed template/resource path, Databricks documents `WorkspaceClient().postgres.generate_database_credential(endpoint=...)` and connection pooling so each new connection receives a fresh token before the one-hour OAuth credential expires. Source: [Connect a custom Databricks app to Lakebase](https://docs.databricks.com/aws/en/oltp/projects/tutorial-databricks-apps-autoscaling).

## Free Edition Caveats

- Free Edition is no-cost, aimed at learning/prototyping, and Databricks explicitly lists "Build a database application" with Lakebase Postgres as an available Free Edition use case. Source: [Sign up for Databricks Free Edition](https://docs.databricks.com/aws/en/getting-started/free-edition).
- Free Edition is serverless-only and quota-limited. Custom compute configurations are not supported, and outbound internet access is restricted to a limited set of trusted domains. Source: [Databricks Free Edition limitations](https://docs.databricks.com/aws/en/getting-started/free-edition-limitations).
- App limit: up to 3 Databricks Apps per account. Apps run up to 24 hours after being started, updated, or redeployed, then are automatically stopped; they can be restarted. Source: [Databricks Free Edition limitations](https://docs.databricks.com/aws/en/getting-started/free-edition-limitations).
- Lakebase limit: one Lakebase project per account, with scale-to-zero compute. The Lakebase tutorial also notes the first query after a long pause can take a few seconds because Lakebase scales to zero when idle. Sources: [Databricks Free Edition limitations](https://docs.databricks.com/aws/en/getting-started/free-edition-limitations), [Using Lakebase with Databricks Apps](https://docs.databricks.com/aws/en/oltp/projects/databricks-apps).
- Free Edition has no guaranteed reliability, support, or SLA; usage quotas can shut down compute for the rest of the day, and in extreme cases the rest of the month, while preserving data/settings. Source: [Databricks Free Edition limitations](https://docs.databricks.com/aws/en/getting-started/free-edition-limitations).
- Administrative caveats relevant to app planning: one workspace and one metastore per account, no account console/account-level APIs, no compliance enforcement/security customization/private networking configurations, and no SSO or SCIM support. Free Edition is intended for non-commercial use. Source: [Databricks Free Edition limitations](https://docs.databricks.com/aws/en/getting-started/free-edition-limitations).
